{# EVERY REQUEST THIS PANEL MAKES IS AN `hx-get`, and nothing here has a submit handler. The first version did, and it was wrong in a way worth recording: an async function returns a PROMISE, which is truthy, so `onsubmit="return search()"` handed the browser a go-ahead — the page reloaded mid-request and the cancelled fetch surfaced as "could not reach the server". TWO TRIGGERS BECAUSE THERE ARE TWO COSTS. Typing reads what this instance already holds: an index lookup, no outbound call, so it can run on a debounce. Enter and the button ask the SERVICES, which spends requests against somebody else's rate limit, so it takes a deliberate act. That is the only difference between them — same route, same fragment, one extra value. ENTER IS THE FORM'S OWN SUBMIT, handled by htmx rather than by script. A form carrying `hx-get` intercepts its submit, which is what makes Enter and the button one behaviour instead of two, and is why neither can reload the page. #} {# `hx-boost="false"` BECAUSE THIS FORM IS NOT A NAVIGATION. {# `input`, NOT `keyup`, BECAUSE TEXT ARRIVES WITHOUT KEYS. A paste from the mouse, a cut from the context menu and a browser's own clear button all change the value and press nothing, so a box listening for keyup sat on its old results — measured in Firefox, where a pasted title searched for nothing. `input` fires for every way the value changes and for nothing else, and `changed` still ignores the keys that move the caret. The non-standard `search` event that used to ride beside it is gone with it: Firefox never fires it, and everywhere else it only repeated a request `input` had already made. #} {# WHICH CALENDAR IS BEING SEARCHED, carried as a value rather than read back out of the address bar: it is the same fact the toolbar's picker renders from, so the two cannot disagree. #} {# ASKING THE SERVICES IS A FIELD OF THIS FORM, AND THAT IS WHY.
