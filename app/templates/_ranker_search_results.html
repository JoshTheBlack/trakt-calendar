{# Titles a search found: the inside of #searchResults under the pool's search box, fetched as the box is typed into (/rankings/fragments/search). The results used to arrive as JSON and be built into this markup by a script. A RESULT CARRIES ITS KEY AND THE QUERY THAT FOUND IT, AND NOTHING ELSE ABOUT THE TITLE. Adding one — by a click or by dragging it into a tier — sends those two back, and the server reads the title out of this same search's stored answer (ranker/sources.py's title_from_search). A result used to carry the whole title serialized onto its element for the add to hand back, which let a page decide what was stored. WHETHER A RESULT IS ALREADY ON THE BOARD IS DECIDED HERE. It used to be written on afterwards by a script, because the held set "changes without a request" — which stopped being true once a removal began answering with the whole page. Every way of changing it is a request now, and the one that does not redraw this list is a result DRAGGED into a tier, which marks the one result it dragged (ranker/dnd.js). Nothing sweeps the list against the page's copy of the board any more, which is just as well: that copy is bumped rather than refreshed, so it could mark a result against a board that had moved. CLICKING A RESULT POSTS IT, and the answer is the page with this search still on it — drawn again from the cache the search box's own request filled, so adding a second title from one search costs no second search. The trigger refuses a held result rather than the page checking afterwards, because a drag can end in a click on the result it just added.
