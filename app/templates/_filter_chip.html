{# One filter chip: a token, and which of the three answers it currently carries. THREE RADIOS, NOT A BUTTON WITH A VALUE, and it is the same argument _filter_badge.html makes for the card badges: the browser holds the choice, the stylesheet reads it (`:has(:checked)`), and no state is kept anywhere for anything to fall out of step with. It also means the panel's Cancel is `form.reset()` and its save is the form's own values — neither needs a script that knows what a chip is. THE RADIOS ARE THE KEYBOARD CONTROL AND THE LABELS ARE THE POINTER ONE. A radiogroup already does arrow-key cycling, labelling and ARIA properly, so the real inputs are what a keyboard reaches; the visible face is a LABEL hidden from assistive tech, existing only so that a pointer can cycle the three in one press instead of three. THE CYCLE IS THE MARKUP. Each radio is followed by the label that belongs to the answer AFTER it, and the stylesheet draws only the label whose radio is checked — so "grey, then only these, then not these, then grey" is three `for` attributes and a `:checked +` rule. It used to be a click listener and a three-element order in a script, and neither knew the cycle any better than the browser does. THE ids ARE POSITIONAL, not built from the token, because a token is free text — "Talk Show", a network with a slash in it — and an id with a space in it is an id nothing can point `for` at. `index` is the chip's place in its field, so the field's own name plus that number is unique on the panel without the token appearing in it at all. THE NAME CARRIES THE DESTINATION. `chip::` is spelled by app/calendar/vocab.py's `field_name` and parsed back by the same module, so this template never spells the format itself.
