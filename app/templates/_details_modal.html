{# THE DETAILS PANEL'S SHELL, AND THERE IS ONE OF IT. The calendar, the tracker and the public share page each drew this box for themselves, with their own element ids and their own close function, and the layout inside was the same three times over. Two of the copies had drifted apart in what they carried; the third had no room reserved for the actions bar at all. A shell is not something a page has an opinion about, so it is here. THE ids ARE THE CONTRACT WITH THE FRAGMENT. `detailsBody` is what every details fragment is swapped into and `detailsTitle` is the heading the opening click sets, so a page including this file needs to know nothing else about how the panel is filled — see `openDetailsPanel` in static/js/ui.js. NOTHING HERE SAYS HOW IT CLOSES. The backdrop click, Escape and the button all go through `closeModal` in static/js/ui.js, which is the one place that knows what closing means — a playing trailer has to be torn down rather than hidden, and that was a property of one call site until it became a property of closing. This markup used to carry its own `onclick` for the backdrop, as seven other overlays did and six did not. `detailsActions` IS ALWAYS HERE AND USUALLY EMPTY. The add-to-library buttons are the calendar's and admin-only; its details route draws them from the server's own record of which services are reachable and what each library holds, and _details.html delivers them here out-of-band. Opening the panel empties the slot (static/js/ui.js), so one title's buttons never sit over the next one's panel. Reserving the slot on every page is what stops a second shell being drawn the day another surface wants one. #}

{# THE TWO STATES THE SERVER CANNOT RENDER, AS MARKUP RATHER THAN AS STRINGS IN A SCRIPT. One is shown before the request has been answered and the other when it could not be answered at all — a dropped connection, a lapsed session, a limit — which are exactly the cases where there is no response to swap in. Both are CLONED by static/js/ui.js rather than built there, so every piece of markup this panel can show is written in a template, including the two that arrive without a round trip. `data-details-pending` IS WHAT SAYS "NOTHING HAS LANDED HERE YET", and it is read rather than inferred for a measured reason: htmx runs its swap step for a response on the no-swap list too, marking the request swapped, and the swap itself is then a no-op — so the request context reports success for a 404 that put nothing on the page. Whether this marker is still here afterwards is the only reliable answer, and it is a fact about the DOM rather than about the library. Every refusal the server CAN state renders as a fragment of its own (_details_gap.html), because the server is the only side that knows which refusal it is. #}
